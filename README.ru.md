# dsh-cron

Английская версия: [README.md](README.md)

`dsh-cron` добавляет в DeepSeek Harness агентов по расписанию. Задача — это один
промпт плюс расписание; каждый запуск идёт в отдельном процессе `dsh`, без
оператора, и оставляет после себя запись и сводку. Человек видит и правит весь
набор задач на странице настроек в веб-интерфейсе, а модель создаёт, читает,
ставит на паузу и удаляет задачи обычными инструментами. Определения — это
обычные YAML-файлы, поэтому всё, что записывает плагин, остаётся редактируемым
руками и совместимым с плагином-планировщиком, который уже владеет этими файлами.

## Зачем это нужно

В состав харнесса входит `@deepseek-ai/dsh-schedule` — напоминания, привязанные к
сессии: они приходят как обычные сообщения в той же беседе, а для доставки нужен
живой корневой агент. Есть и отдельный плагин-планировщик
(`@dsh-routines/bundle`): он выполняет промпты по cron из YAML-файлов в
`.dsh/routines/`, но управляется из терминала — `dsh routines list`,
`dsh routines logs`, `dsh routines pause` — без страницы настроек в веб-интерфейсе
и без инструментов для модели. Не хватало ровно половины, которая связывает и то
и другое с людьми и моделями: человек не мог *увидеть и отредактировать*
расписание там, где он уже работает, а у модели не было полноценных инструментов,
чтобы его *создать*. `dsh-cron` — это и есть недостающая половина. Он читает и
записывает тот же формат определений, состояния и записей о запусках, который уже
использует `dsh-routines` (см.
[Совместимость и сосуществование](#совместимость-и-сосуществование)), то есть
дополняет его, а не заменяет.

## Установка

```console
dsh plugin --profile <profile> add github:seoeaa/dsh-cron
dsh --profile <profile>
```

- `<profile>` — профиль, в который ставится плагин (`web`, `headless`, …).
  Команда `dsh plugin` передаёт свои аргументы в pnpm внутри каталога профиля, а
  затем добавляет в `dsh.profile.bundles` все установленные пакеты, объявившие
  патч `dsh.bundle`, поэтому одной этой команды достаточно и для установки, и для
  монтирования. Скрипт `prepare` этого пакета собирает обе половины, поэтому для
  установки нужны его devDependencies.
- `<owner>` — аккаунт GitHub, в котором лежит этот репозиторий; форма `github:` не
  требует публикации в реестре.
- **Профиль должен быть запущен, иначе задачи не сработают.** Цикл опроса, который
  запускает задачи, живёт в хостовой половине плагина — в этом же процессе. Пока
  профиль остановлен, запусков нет. После запуска первый опрос видит все моменты,
  прошедшие с последнего записанного запуска, и догоняет их по одному на задачу за
  опрос: самый ранний запускается, а остальные, пока этот запуск идёт, либо
  пропускаются, либо запускаются — по политике пересечений — пока опорный момент не
  дойдёт до текущего времени.
- Страница настроек появляется в разделе **Настройки → Задачи по расписанию**
  (идентификатор секции `cron`). На ней ровно те же задачи, что видят
  инструменты и цикл опроса: одно хранилище, один файл состояния.

Проверить, что строка плагина собралась:

```console
dsh --profile <profile> --dump-config | grep -A6 'id: cron-store'
```

## Что такое задача

Одна задача — один YAML-файл. Поля:

| Поле | Обязательно | Значение |
| --- | --- | --- |
| `name` | да | Идентификатор задачи: `[a-z0-9][a-z0-9-]*`, не длиннее 64 символов. Он же — имя файла определения и префикс записей о запусках. |
| `schedule` | да | Пятипольный cron, макрос `@…` или интервал (`every 30m`). |
| `timezone` | нет | Зона IANA для расчёта расписания. По умолчанию — `defaultTimezone` плагина (`UTC`), но никогда не зона хоста. |
| `prompt` | да | Полный промпт одного запуска, выполняемый в свежей сессии без памяти о беседах. |
| `cwd` | нет | Рабочий каталог запуска; туда же попадают запись и сводка. По умолчанию — каталог проекта. `~/…` раскрывается. |
| `profile` | нет | Профиль DSH, который поднимает запуск. По умолчанию `headless`. |
| `overlap` | нет | `skip` (по умолчанию), `queue` или `cancel-previous` — что делать, если предыдущий запуск ещё идёт. |
| `timeoutMin` | нет | Жёсткий предел в минутах, 1–1440. По умолчанию `45`. |
| `deliver` | нет | Куда уходит готовя сводка: `file` и/или `chatnode`. По умолчанию `file` — файловая сводка пишется всегда. |

Каталоги:

- область проекта: `<projectDir>/.dsh/routines/<name>.yaml`
- глобальная область: `$DSH_HOME/routines/<name>.yaml`, то есть
  `~/.dsh/routines/<name>.yaml`, если `DSH_HOME` не задан

`projectDir` — это каталог, из которого запущен профиль, если в строке
конфигурации не указано иное. Определение из проекта перекрывает глобальное
определение с тем же `name`. Файл, который не разбирается или не проходит
проверку, показывается в панели и пропускается: он не скрывает остальные задачи и
не останавливает цикл опроса.

Полный пример:

```yaml
name: nightly-tests
schedule: "0 2 * * *"
timezone: Europe/Moscow
prompt: |
  Запусти полный набор тестов в этом каталоге. Ничего не исправляй: напиши, что
  упало, и для каждого падения приведи первую упавшую проверку. Отчёт — по-русски,
  не длиннее 15 строк.
cwd: /srv/app
profile: headless
overlap: skip
timeoutMin: 45
deliver:
  - type: file
```

Ту же задачу можно создать из беседы (`cron_create`) или в панели (`Новая
задача`) — в обоих случаях пишется этот файл.

## Расписания

Поддерживаемые формы поля `schedule`:

| Форма | Примеры |
| --- | --- |
| Пятипольный cron: `минута час день-месяца месяц день-недели` | `0 2 * * *`, `*/15 * * * *`, `30 8 * * 1-5` |
| Макросы | `@hourly`, `@daily`, `@midnight`, `@weekly`, `@monthly`, `@yearly`, `@annually` |
| Интервалы | `every 30m`, `every 4h`, `every 90s`, `every 2h30m` |

Внутри поля:

- списки `1,2,3`; диапазоны `9-17`; шаги `*/15`, `9-17/2`; их сочетания.
- трёхбуквенные имена без учёта регистра: месяцы `jan`…`dec`, дни недели
  `sun`…`sat`. `7` в дне недели означает воскресенье и сводится к `0`.
- `?` принимается как `*`.
- выражения из шести полей (с секундами) **отклоняются** с явной ошибкой: cron
  здесь без секунд. Если нужны секунды — используйте `every 30s`.

Правило сопоставления дней (как в Vixie cron):

- ограничен день месяца, день недели `*` → решает только день месяца;
- ограничен день недели, день месяца `*` → решает только день недели;
- ограничены **оба** → день подходит, если совпало **любое** из полей
  (`0 0 1 * 1` сработает и 1-го числа месяца, и в каждый понедельник).

Время:

- зона задаётся всегда явно: из `timezone` определения либо из `defaultTimezone`
  плагина, если поле отсутствует. Зона машины-хоста не подставляется молча.
- неизвестное имя зоны — ошибка определения, а не тихая подмена на другую зону.
- переходы на летнее время разбираются по реальным моментам: время, попавшее в
  «пропущенный час» при переводе вперёд, не срабатывает, а неоднозначное время при
  переводе назад срабатывает в первом из своих вхождений.
- если совпадений нет примерно в пределах 1600 дней (например, `0 0 30 2 *`), у
  задачи нет следующего запуска и панель показывает `—`.

Проверяйте выражение до сохранения: `cron_preview` в беседе или живой
предпросмотр в редакторе панели. Оба показывают короткое английское описание и
ближайшие моменты срабатывания.

## Веб-панель

Настройки → Задачи по расписанию. Страница рисуется из одного снимка состояния,
полученного с хоста, и не хранит ничего, кроме последнего загруженного снимка.

- **Панель инструментов** — имя и версия плагина, `Обновить`, `Новая задача`.
  Обновление — по требованию: хост не присылает изменения в браузер сам.
- **Баннер движка** — либо «Этот плагин выполняет задачи по расписанию.», либо
  «Расписанием управляет `<сервис>`.» с причиной и пометкой, что страница в этом
  случае только редактирует определения. Это ответ на вопрос «кто планирует?».
- **Некорректные файлы определений** — каждый файл, который не разобрался, с
  одной строкой причины. Такие файлы пропускаются, пока их не исправят.
- **Куда попадают сводки** — файловая сводка всегда пишется рядом с `cwd` задачи;
  остальные доступные получатели (узел беседы) перечисляются с пометкой о
  доступности.
- **Таблица задач** — по строке на задачу:
  - `Имя`, с бейджами `пауза` и `выполняется`;
  - `Расписание` — человеческое описание плюс исходное выражение;
  - `Часовой пояс`, `Источник` (`проект`/`глобальная`), `Пересечения`,
    `Профиль`;
  - `Следующий запуск` — относительно («через 3ч»), в подсказке абсолютное время;
  - `Последний запуск` — индикатор статуса, сам статус (`завершена`, `ошибка`,
    `тайм-аут`, `пропущена`, …) и сколько времени прошло; в подсказке — абсолютное
    время и текст последней ошибки;
  - `Рабочий каталог` — сокращённый путь, в подсказке полный;
  - `Действия` — `Запустить сейчас`, `Пауза`/`Продолжить`, `Изменить`, `История`,
    `Копировать промпт`, `Удалить`. Удаление сначала спрашивает подтверждение
    прямо в строке и объясняет последствия: файл определения удаляется, история
    запусков остаётся на диске.
- **Редактор** — `Новая задача` или `Изменить`. Поля: имя (проверяется по тому же
  правилу, что и на хосте), расписание (выбор шаблона плюс исходное выражение, с
  живым описанием и тремя ближайшими запусками, которые считаются локально прямо
  при вводе), часовой пояс (с подсказками частых зон; должна быть корректная зона
  IANA), промпт, рабочий каталог (пусто — значит каталог области), профиль,
  пересечения, тайм-аут в минутах, получатели сводки и область, которая решает, в
  какой каталог будет записан файл. Кнопка сохранения недоступна, пока хоть одно
  поле некорректно; отказ хоста показывается внутри диалога.
- **История** — по задаче, от новых к старым, с группировкой по локальным дням
  (`Сегодня`, `Вчера`, далее дата). В каждой записи: статус, время запуска,
  относительное время, длительность, идентификатор сессии, сводка (длинная
  сворачивается под кнопку), автоматически отклонённые вызовы инструментов,
  результаты доставки и текст ошибки. История доступна только для чтения: это
  запись, которую оставил запуск.

Подробно по каждому элементу управления, с указанием файла или сервиса, которых
касается каждое действие: [docs/panel.md](docs/panel.md).

## Инструменты

| Инструмент | Что делает | Заметные параметры |
| --- | --- | --- |
| `cron_list` | Перечисляет задачи: расписание, зона, ближайший и последний запуск, пауза/выполняется, а также файлы определений, которые не разобрались. Вызывайте перед созданием, правкой или удалением, чтобы имя было свободным. | — |
| `cron_get` | Показывает одну задачу целиком, включая её промпт и путь к определению. | `name` |
| `cron_preview` | Проверяет расписание без сохранения: описание, нормализованная пятипольная форма, три ближайших запуска. | `schedule`, `timezone?` |
| `cron_create` | Создаёт задачу или перезаписывает её по имени. | `name`, `schedule`, `prompt`, `timezone?`, `cwd?`, `profile?`, `overlap?`, `timeoutMin?`, `deliver?`, `scope?` |
| `cron_update` | Меняет только переданные поля, остальные сохраняют текущие значения. Может перенести определение между областями. | `name` и любые поля из `cron_create` |
| `cron_delete` | Удаляет определение. История запусков остаётся на диске. | `name` |
| `cron_pause` | Останавливает срабатывания; определение и история сохраняются. | `name` |
| `cron_resume` | Возвращает задачу к срабатываниям по расписанию. | `name` |
| `cron_run` | Запускает задачу немедленно и ждёт завершения. Это настоящий запуск без оператора; используйте его для проверки задачи, но не в цикле. | `name` |
| `cron_logs` | Последние запуски задачи: статус, время, длительность, сводка, идентификатор сессии, ошибки. | `name`, `limit?` (по умолчанию 10) |
| `cron_targets` | Перечисляет, куда сейчас можно доставить готовую сводку. | — |

`deliver` принимает `file` и `chatnode`; файловая сводка пишется рядом с рабочим
каталогом задачи всегда, что бы ни было в списке.

Когда модели стоит браться за эти инструменты — в плагине есть runtime-навык
(`cron`), который описывает это и доступен всегда, пока смонтирован плагин:

- Планируйте работу только тогда, когда она должна случиться **позже или снова**.
  Если запрос можно выполнить сейчас, в этой беседе, — выполняйте сейчас и задачу
  не создавайте. Никогда не создавайте задачу «на всякий случай».
- Прежде чем что-то создавать, найдите ответы: что именно выполняется
  (самодостаточный промпт — у запуска нет памяти о беседе и некого спросить),
  когда (конкретное выражение и та зона IANA, которую имеет в виду пользователь),
  где (рабочий каталог) и сколько (тайм-аут и политика пересечений — обычно
  пользователь имеет в виду `skip`).
- Согласуйте время с пользователем, проверьте выражение через `cron_preview`,
  затем `cron_create`, а потом `cron_run` один раз, если пользователь хочет
  доказательство работоспособности.
- Сообщите имя задачи, когда она сработает в следующий раз и что будет в сводке.

## Безопасность запусков без оператора

Запуск — это процесс, а не ход агента внутри текущего процесса, и он устроен так,
чтобы безопасно завершаться, когда за ним никто не смотрит.

- **Свой процесс.** Родитель запускает
  `dsh --profile <profile> --patch <оверлей> -- <промпт>` в `cwd` задачи.
  Зависший запуск не может уронить хост, а его падение — это код возврата,
  который родитель записывает.
- **Политика подтверждений принудительно `never`.** Сгенерированный оверлей
  ставит политику подтверждений `never` и подключает соответствующий пресет
  разрешений `workspace-write-deny`, поэтому всё, что запросило бы подтверждение,
  отклоняется сразу. Отклонённые вызовы попадают в запись о запуске (`denied`) и
  видны в истории панели и в выводе `cron_logs`/`cron_run` — именно по этому
  списку видно, что задаче нужна более широкая политика.
- **Никакого вложенного планирования.** Оверлей по идентификаторам отключает
  строки планировщиков (этого плагина и `routines-scheduler`) и строку панели, а
  штатный headless-раннер заменяет на `dsh-cron/run`. Запуск не должен планировать
  другие запуски — ни из этого плагина, ни из любого другого.
- **Жёсткий тайм-аут.** `timeoutMin` (по умолчанию 45, максимум 1440). По
  истечении процесс получает `SIGTERM`, а если через 10 секунд всё ещё жив —
  `SIGKILL`; статус записи становится `timeout` с пояснением.
- **Политика пересечений.** `skip` (по умолчанию) пишет запись `skipped` и
  сдвигает опорный момент; `queue` оставляет задачу «должной», и она сработает на
  первом опросе после завершения текущего запуска; `cancel-previous` останавливает
  идущий процесс (причина `superseded by the next scheduled run`), после чего
  замена запускается на одном из следующих опросов — когда остановленный процесс
  уже завершился: у задачи одновременно может идти только один запуск, поэтому
  заменить его в том же опросе нельзя.
- **Полный лог сессии на каждый запуск.** Каждый запуск получает свежую сессию, а
  её идентификатор записывается (`sessionId`), так что запуск можно воспроизвести
  позже.
- **Запись и сводка.** Источник истины —
  `<cwd>/.dsh/routines/runs/<runId>.json`; рядом пишется человеческая сводка
  `<runId>.md`. Оба файла пишутся атомарно.
- **Как собирается сводка.** Если последнее сообщение ассистента достаточно
  короткое (по умолчанию до 2000 символов), сводкой становится оно; иначе
  транскрипт запуска сжимается отдельным вызовом модели, а если этот вызов не
  удался, берётся начало сообщения с явной пометкой об усечении.

## Совместимость и сосуществование

`dsh-cron` намеренно делит свои артефакты с плагином-планировщиком `dsh-routines`,
чтобы уже настроенная установка продолжала работать:

- **Определения** — те же два каталога, те же имена полей, те же значения по
  умолчанию и то же правило «проект перекрывает глобальную область по `name`».
  Файл, записанный одним движком, читается другим.
- **Состояние** — `<projectDir>/.dsh/routines/state.json` с ключами, которые
  использует `dsh-routines` (`paused: string[]`, `lastRunAt: Record<string, number>`),
  плюс наш дополнительный ключ `lastStatus` (последний статус и ошибка по каждой
  задаче — для таблицы). Неизвестные ключи игнорируются при чтении. Свой файл
  состояния плагин записывает из известных ему ключей, поэтому посторонние ключи
  третьего движка в этом файле не переживут паузу или возобновление, сделанные
  отсюда.
- **Записи о запусках** — `<cwd>/.dsh/routines/runs/<runId>.json` плюс `<runId>.md`.
  Записи, которые плагин не может разобрать, пропускаются при чтении и никогда не
  удаляются очисткой.
- **Запись файлов** — определения и состояние пишутся через временный файл и
  переименование, поэтому читатель видит либо старый файл, либо новый, но не
  недописанный файл.
- **Правки руками** — оба каталога определений отслеживаются (с подавлением
  дребезга), поэтому правка YAML появляется в панели и в инструментах без
  перезапуска.

Кому принадлежит планирование, когда установлено больше одного планировщика:

| `engine` | Поведение |
| --- | --- |
| `auto` (по умолчанию) | Если смонтирован другой планировщик (cordis-сервис `routinesScheduler`), этот плагин ничего не планирует, но сохраняет инструменты, хранилище и страницу — и сообщает об этом баннером в панели. Иначе планирует. |
| `own` | Этот плагин планирует независимо от того, что ещё смонтировано. Это переключатель, который ставят после отключения другого планировщика; если работают оба, срабатывают оба. |
| `off` | Этот плагин никогда не планирует: определения, инструменты, история и страница продолжают работать, а баннер панели сообщает, что планирование здесь отключено. |

## Конфигурация

У каждого поля есть значение по умолчанию, поэтому плагин полезен даже с пустой
строкой конфигурации. Поля задаются в строке бандла в `cordis.patch.yml` профиля
(при переопределении строки перечисляйте все ключи заново).

| Поле | По умолчанию | Что меняет |
| --- | --- | --- |
| `projectDir` | `process.cwd()` | Каталог, в `.dsh/routines/` которого лежат определения области проекта и файл состояния. Он же — каталог, из которого печатается отчёт запуска, и значение по умолчанию для отсутствующего `cwd`. |
| `globalDir` | `$DSH_HOME/routines` (`~/.dsh/routines`) | Каталог глобальных определений. `~/…` раскрывается. |
| `engine` | `auto` | Кто планирует: `auto`, `own`, `off`. См. таблицу выше. |
| `tickSeconds` | `20` | Секунды между опросами наступивших моментов (5–3600). Меньше — точнее ловится момент, но больше пробуждений. |
| `dshBin` | `dsh` (переопределяется `$DSH_BIN`) | Бинарник для подпроцессов запуска. Если его нет в `PATH` запуска, запуск падает с ошибкой порождения процесса в своей записи. Путь к файлу `.js`/`.mjs`/`.cjs` выполняется текущим Node. |
| `defaultProfile` | `headless` | Профиль, который поднимает запуск, если определение не называет свой. Важно: хранилище само подставляет `headless`, поэтому сейчас это поле — документация, а не рабочий переключатель. |
| `defaultTimezone` | `UTC` | Зона для определения, в котором она не указана, и для `cron_preview`, когда вызывающий не передал зону. |
| `defaultTimeoutMin` | `45` | Тайм-аут для определения, в котором он не указан. Важно: хранилище само подставляет 45, поэтому сейчас поле не читается. |
| `allowRunNow` | `true` | Разрешает `Запустить сейчас` в панели и инструменту `cron_run` запускать задачу вне расписания. `false` оставляет только запуски по расписанию. |
| `maxHistoryPerJob` | `50` | Задуманный предел числа хранимых записей о запусках на задачу. Важно: очистка пока никем не вызывается, поэтому поле сейчас ни на что не влияет. |
| `watch` | `true` | Следить за обоими каталогами определений и перечитывать хранилище при правках руками. |
| `digestMaxChars` | `2000` | Последнее сообщение ассистента не длиннее этого значения *и есть* сводка; более длинное — сжимается. |
| `summaryMaxChars` | `24000` | Ограничение транскрипта, который передаётся вызову-суммаризатору. |
| `summaryMaxTokens` | `400` | Предел выходных токенов этого вызова. |
| `summaryTimeoutMs` | `60000` | Общий предел времени на вызов-суммаризатор. |
| `runModule` | скомпилированный `lib/run.js` этого пакета | Абсолютный путь к модулю, который подпроцесс запуска монтирует как драйвер. Вычисляется от установленной копии; переопределяйте только для разработки. |

## Как проходит запуск

1. **Опрос.** Каждые `tickSeconds` планировщик спрашивает, у каких задач момент
   срабатывания наступил не позже текущего времени, считая от последнего
   записанного запуска задачи (задача, которая ещё не запускалась, отсчитывается
   на один такт назад, поэтому новое определение не воспроизводит историю). Один
   опрос выполняется сразу при монтировании плагина — так догоняются моменты,
   пропущенные за время простоя профиля: по одному на задачу за опрос, начиная с
   самого раннего.
2. **Опорный момент.** Запланированный момент пишется в `state.json`
   (`lastRunAt` и `lastStatus: running`) *до* появления подпроцесса. Поэтому
   падение в середине запуска не может повторно вызвать тот же момент.
3. **Оверлей.** Генерируется патч для одного запуска
   (`.<runId>.patch.yml` в каталоге запусков задачи): подтверждения `never`,
   отключённые строки планировщиков и панели, и `dsh-cron/run` вместо штатного
   раннера.
4. **Подпроцесс.** `dsh --profile <профиль> --patch <оверлей> -- <промпт>`
   стартует в `cwd` задачи. Сначала пишется запись `running`, поэтому панель и
   инструменты видят запуск в момент старта, а не в момент завершения.
5. **Свежая сессия.** Драйвер создаёт новую сессию, один раз отправляет промпт,
   ждёт, пока агент освободится, и сбрасывает лог сессии на диск.
6. **Запись.** Статус, код возврата, длительность, идентификатор сессии, сводка и
   отклонённые подтверждения пишутся в `<runId>.json` и `<runId>.md`. Родитель
   сводит эту запись с кодом завершения процесса (`completed`, `timeout` или
   `failed`) и добавляет результаты доставки.
7. **Доставка.** Файловая сводка уже лежит на диске. Доставка `chatnode` идёт
   через `ctx.chatnode`, если узел беседы смонтирован; если его нет, попытка
   записывается как неудачная доставка, но запуск из-за этого не считается
   проваленным.
8. **Статус.** Завершение обновляет `state.json`, поэтому колонки «Следующий
   запуск» и «Последний запуск» в панели, а также `cron_list` и `cron_logs`
   показывают одно и то же. Если смонтирован реестр фоновых задач, запуск
   регистрируется в нём как задача вида `cron` — с возможностью отмены и сводкой
   в качестве вывода.

## Разработка

```console
pnpm install
pnpm run typecheck   # хостовая половина и клиентская половина
pnpm run build       # lib/index.js (хост) и lib/client.js (браузер)
pnpm test            # vitest
```

- Хостовая половина: `tsc -p tsconfig.json` выдаёт ESM-модули и декларации в
  `lib/`.
- Клиентская половина: `tsdown` собирает `src/client/index.ts` в `lib/client.js` —
  бандл-фабрику (`window.__ModuleLoader__.load(...)`), которая берёт React и
  клиентские пакеты харнесса из таблицы модулей оболочки, а всё остальное
  встраивает внутрь. Стили поставляются строкой из `src/client/styles.ts` и
  устанавливаются в один элемент `<style data-dsh-cron>`.
- В `package.json` экспорты: `.` → `lib/index.js`, `./typert` →
  `lib/typert.host.js`, `./client` → `lib/client.js`.

## Ограничения

- **Каждый запуск — это полноценный прогон агента.** Задача стоит нового
  процесса `dsh`, новой сессии агента и новой беседы с моделью на каждое
  срабатывание, плюс запуск процесса и модели сверху. Задача раз в 15 минут — это
  96 запусков в сутки.
- **Панель обновляется по требованию.** Канала push нет: страница обновляется при
  загрузке, по кнопке `Обновить` и после каждого вашего действия.
- **Сводка всегда попадает в файл.** Доставка в узел беседы работает только если
  что-то предоставляет `ctx.chatnode`; иначе попытка записывается как неудачная.
  Больше ничего не доставляет (ни почты, ни уведомлений).
- **Модель ничего не узнаёт о запуске, пока не спросит.** Вывод запуска никогда не
  подмешивается в беседу; модели нужно вызвать `cron_logs` (или `cron_run`).
- **`Запустить сейчас` и `cron_run` — это настоящие запуски** и стоят столько же,
  сколько запуск по расписанию. Отключите их через `allowRunNow: false`, если
  профиль должен ходить только по расписанию.
- **Записи о запусках пока не очищаются.** Они накапливаются в `cwd` каждой
  задачи; поле `maxHistoryPerJob` объявлено, но ни один вызов его не использует.
- **Область определения не исключает вторую.** Если сохранить задачу в область
  проекта под именем, которое уже есть в глобальной области, глобальный файл будет
  затенён, а не заменён; `Удалить` удаляет сначала копию в проекте, потом
  глобальную.
